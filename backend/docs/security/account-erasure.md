# Platform-admin account erasure

`DELETE /api/v1/admin/users/{user_id}` is the platform-admin account-erasure path. The Data
Deletion screen calls this endpoint after the operator completes recent MFA reauthentication and
types `DELETE <account email>`; the server checks the exact phrase. The currently signed-in account
and configured bootstrap administrator accounts are protected. Account erasure is immediate for
live database rows; queued object-storage cleanup and backup expiry can take longer.

The transaction revokes sessions and removes the target account, account-owned relational records,
provider credentials and assignments, personal queries and documents, support tickets and submitted
feedback, account-authored replies, and user-created document automation and sharing configuration.
It also removes personal usage records, DeepSpace mission snapshots and task records, temporary
library upload chunks, MCP events generated by the account, and a workspace-purge request made by
the target. Notifications delivered to other users are retained with a generic actor-free message.
If a purge is already processing, account erasure returns `409 ACCOUNT_DELETION_IN_PROGRESS` so the
two operations cannot race. In a tenant with other users, their account-owned records and shared
tenant records remain. If the deleted account was the tenant's last member, the tenant is removed.

Before relational rows are deleted, the service creates durable cleanup jobs for account-owned
document files, dataset derivatives, support attachments, Qel Connect media, DeepSpace media and
Library versions, and temporary Library upload chunks. Those jobs are committed with the database erasure. The response reports
`pending_storage_cleanup_count`. `maintenance.storage_cleanup` retries pending work. The admin page
shows pending and exhausted jobs without exposing object keys or raw provider errors; an authorized
platform admin can manually requeue a failed job. When an object is removed, its cleanup row and
stored locator are deleted. If provider storage remains unavailable, the job stays failed until an
operator retries it or resolves the provider issue.

Audit events attributed to the erased account keep only minimal anonymous security metadata: action,
time, status, tenant, and trace reference. Actor ID, IP address, resource reference, and event detail
are cleared. A separate `admin.user.account_erased` event records the acting administrator, the
erased account's opaque user ID, and the number of file cleanup jobs; it does not record the deleted
user's email. This target ID supports the administrator's security-history filter and is retained
for the audit period (90 days by default). Other audit rows follow the same configured retention.

Password failures for unknown accounts and OAuth callback failures or cancellations are recorded as
anonymous platform-level events. They contain the authentication method and a bounded failure reason,
not the submitted email, password, OAuth code, or client IP. These events are visible in the global
Audit Logs view and are removed by the configured audit retention job.

This erases live AverQel database records and application-owned object files after cleanup succeeds.
It does not immediately erase backup copies or data already sent to external providers, which follow
the deployment's backup schedule and each provider's own retention and deletion controls. Never
describe the operation as immediate deletion from every backup or third-party system.

The tenant-data purge API at `/api/v1/admin/data-deletions` is separate from account erasure. It
removes tenant content while retaining user accounts and selected operational records. A second
authorized platform administrator can approve immediately. For a single-owner installation, the
requester can approve their own request only after the configured hold (24 hours by default, bounded
to 24–168 hours); recent MFA is required for request, approval, self-approval, and cancellation. The
worker rechecks the persisted approval mode and hold before processing. The requester can cancel while
the request is awaiting approval. Every action is audited.
